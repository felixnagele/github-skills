# OctoAcme Project Management Docs

## Overview

OctoAcme uses a structured, repeatable approach to project management grounded in customer-first values, iterative delivery, clear ownership, and data-informed decision-making. Every project follows a defined lifecycle — from **initiation** (validating a business need, aligning stakeholders, and producing a lightweight project charter) through **planning** (scoping work, identifying dependencies, and setting milestones), into **execution and tracking** (sprint-based delivery with regular standups, progress reviews, and continuous backlog refinement), and finally **release** (coordinated deployment, verification, and stakeholder communication). Each stage has documented checklists, templates, and owner responsibilities to keep teams aligned and reduce ambiguity.

Risks and cross-team communication are managed proactively throughout the project. A living Risk Register captures each risk's impact, likelihood, owner, and mitigation plan, and is reviewed at weekly syncs. Stakeholder communication follows a predictable cadence — weekly PM/PdM syncs, twice-weekly team standups, monthly stakeholder updates, and a defined escalation path (team → PM → Product Lead → Sponsor) for blockers or incidents. Standardised status-update and incident-communication templates ensure consistent, clear messaging across all audiences.

Project roles at OctoAcme are clearly defined to avoid ambiguity and duplication of effort. **Project Managers** coordinate schedules, risks, and cross-team communication. **Product Managers** own the product vision, prioritise the backlog, and measure outcomes. **Developers** design, build, and test features to meet acceptance criteria, while **QA/Testing** validates quality and the Definition of Done. All roles participate in retrospectives after every release cycle, capturing learnings and continuous-improvement action items that feed directly back into upcoming planning cycles.

Quality assurance and continuous improvement are woven into every stage. Acceptance criteria and a shared Definition of Done gate each increment, while post-release retrospectives surface process gaps and drive refinements. OctoAcme treats these process documents as **living documentation** — they are updated as practices evolve and serve as a central, single source of truth for onboarding new team members, aligning stakeholders, and guiding day-to-day project work.

## Purpose of These Documents

These documents centralise OctoAcme's institutional knowledge about how projects are managed. They serve three primary purposes:

1. **Onboarding** — New team members can read these docs to quickly understand how OctoAcme runs projects, what is expected of each role, and where to find templates and checklists.
2. **Day-to-day reference** — Practitioners use these docs as a single source of truth for process steps, templates, and quality gates throughout a project's lifecycle.
3. **Continuous improvement** — As OctoAcme's practices evolve, these docs are updated to reflect current best practices, ensuring the whole organisation benefits from lessons learned.

## How to Use and Update These Docs

- **Using the docs**: Navigate to the relevant document in the table above and follow the checklists, templates, and guidance for your current project stage.
- **Updating the docs**: These are living documents. If you identify a gap, have a process improvement suggestion, or need to add new content, please open an issue using the [Add/Update Content to Project Management Process Docs](../.github/ISSUE_TEMPLATE/add-update-content-to-process-docs.yml) issue template. The template will guide you through describing the change, the rationale, and suggested content.
- **Review**: Significant changes to process docs should be reviewed with relevant stakeholders before merging, consistent with OctoAcme's principle of psychological safety and collaborative decision-making.
